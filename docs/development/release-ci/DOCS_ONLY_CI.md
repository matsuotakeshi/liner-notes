# 文書だけを変更する場合のCI

マニュアルやHELPの誤記修正では、アプリの再ビルドや検証VMでの実行試験は不要です。
この場合も、文書の生成・リンク・検索・配布形式の検証は実行します。
恒久方針は [CI_CD.md](../../../CI_CD.md#文書のみの変更) を参照してください。

## 実行する検査

| 変更内容・実行方法 | 文書検証・軽量検査 | アプリビルド・実行試験・パッケージ |
| --- | --- | --- |
| 許可リストに含まれる文書だけのPR/main更新 | 実行 | 対象外 |
| 文書とソース・設定・CI等の混在 | 実行 | 実行 |
| 差分の比較不能・空差分・未知のファイル | 実行 | 実行 |
| Actionsの手動実行 | 実行対象のワークフローに従う | 省略しない |
| `release/**`・タグの判定 | 実行対象のワークフローに従う | 省略しない |

タグだけでは新しいワークフローは起動しません。上表は既存ワークフローから判定が呼ばれた場合の規則です。
バージョンやビルドスクリプトの変更は文書変更ではありません。

## 文書として扱うファイル

許可リストの正本は [ci/change_scope.py](../../../ci/change_scope.py) です。
ルートMarkdown、ライセンス、`docs/`内のMarkdown・テキスト・画像、既知のマニュアルJSON、
`help/ja/*.txt`・`help/en/*.txt`を対象とします。
`docs/`配下でもPythonや設定ファイル、未知のJSONを追加すると全検証になります。
実行可能ビットやシンボリックリンクの変更も対象外にはしません。

PRは分岐点からの全変更、pushは更新前から更新後までの全変更を確認します。
「最後のコミットだけが文書」でも、同じPR/push内にソース変更があれば省略しません。
名前変更は旧パスと新パスの両方を確認します。

## Actions画面での確認

1. `changes / scope` のJob summaryと `ci-change-scope` Artifactを開きます。
2. `reason: documentation-only`、`build: false`、対象SHAと変更ファイルを確認します。
3. 必須の `linux (almalinux:9)` と `linux (rockylinux/rockylinux:9)` は成功で終了しますが、ビルドステップはskippedです。判定結果を確認した成功であり、ビルド試験を実行した意味ではありません。
4. パッケージ・共有ボード試験・ネイティブ試験の重いジョブはskippedになります。自宅Runner/VMは使いません。ネイティブの最終ゲートは明示的な対象外を受理します。
5. `Canonical manual` は実行され、HTML/Markdown/オフライン版の整合性を確認します。

`FreeBSD Package Source Checks` が起動する場合も共通判定を使います。
文書のみでは軽量な構文・manifest・配布一覧検査を残し、
`Verify real installed-menu package readback` のruntime/dbconvertビルドと実行試験だけを対象外にします。
コード・設定・CI変更を含む場合と手動実行では、この実ビルドと読戻し試験も必要です。

判定失敗、空の判定値、必要な試験の失敗・キャンセルを対象外として受理することはありません。
ブランチ保護は変更せず、必須チェック名も維持します。

## パッケージと正式リリース

文書のみの通常更新ではpkg/RPM/DEBを生成しません。
`Release Set Verification` は、完了したFreeBSDパッケージワークフローの判定Artifactを読み、
同じSHAの文書のみの変更なら成果物照合を対象外にします。前のSHAのパッケージを流用しません。

そのSHAのパッケージが必要な場合は、mainを指定して各パッケージCIを手動実行し、
成功後に同一SHAを指定してRelease Setを手動実行します。必要なネイティブ・互換性試験も
mainで手動実行できます。手動実行では文書判定による省略をしません。

ここでのパッケージ生成・照合は本番配備を許可しません。既存の配備前検査・承認条件は
変わらず、手動CIの結果をpush実行の証跡へ偽装したり、対象外を実行成功と報告したりしません。
