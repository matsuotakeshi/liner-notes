# 送受信コネクタと会員向け送信（stage36〜37）

会員向け送信受付と、進捗表示・中断後の再開・取り消しに対応するPython送信クライアントを追加しました。既存の受信クライアントも同じコネクタ契約へ移しました。

現在実装している転送プロトコルは `line-v1` と [binary-v1](BINARY_TRANSFER.md) です。raw TCPまたはTelnet上で動き、SSHポート転送も利用できます。stage38で、SSH端末向けの独立した [ZMODEM入口](ZMODEM.md) を追加しました。runtimeのTelnet画面内でのZMODEM送受信とXMODEMは未対応です。

## 利用方法

サーバーは従来通り、初期化済み保管庫を指定して起動します。

```sh
make
./runtime --telnet --menu --vault-dir /home/operator/notes-vault 2222 notes.dat members.dat
```

保管庫を有効にしたサーバーでは、停止されていないログイン会員にアップロード権限を付与します。確定したファイルは全会員向けに公開します。承認待ち・カテゴリ別ACLはありません。公開前の予約や一時ファイルは一覧・検索・ダウンロードには出ません。

クライアント側にはPython 3と同じ `scripts` フォルダーを用意します。追加パッケージは不要です。`transfer_connectors.py` も必要なので、スクリプト1本だけをコピーしないでください。

```sh
# 初回送信。--stateには新しいファイル名を指定
python3 scripts/vault-upload.py --host 127.0.0.1 --port 2222 --user bob --state sample-upload.json sample.zip

# 中断後。同じ接続先・会員・元ファイル・stateを指定
python3 scripts/vault-upload.py --host 127.0.0.1 --port 2222 --user bob --state sample-upload.json --resume sample.zip

# 未公開の予約を取り消す。元ファイルは不要
python3 scripts/vault-upload.py --host 127.0.0.1 --port 2222 --user bob --state sample-upload.json --cancel

# 受信。出力先は未作成のパス
python3 scripts/vault-download.py --host 127.0.0.1 --port 2222 --user bob 1 received.zip
```

パスワードはプロンプトで入力します。自動試験向けの `--password-stdin` もあります。コマンドライン引数や再開用ファイルにはパスワードを保存しません。

送信の表示名は元ファイルの名前が初期値です。`--name 表示名` と `--description 説明` で変更できます。元ファイルの内容は変更しません。進捗は標準エラーに、確定したファイルIDとSHA-256は標準出力に表示します。100%はデータ送信完了であり、最終的な公開成功は `Published file` の応答で確認します。

SSHで保護する場合は、先に `ssh -N -L 12222:127.0.0.1:2222 operator@192.0.2.10` を起動し、クライアントに `--host 127.0.0.1 --port 12222` を指定してください。Telnet単体は暗号化していません。

## 再開用ファイル

JSON形式のstateには、接続先、会員名、コネクタ名、元ファイルの絶対パス、サイズ、SHA-256、表示名、説明、転送ID、状態を記録します。ローカルのファイル名・パス情報を含むため、利用者自身で保管してください。既存stateを初回送信で上書きしません。

再開時は元ファイル全体を照合し、サーバーの予約状態・受信位置・期待ハッシュを問い合わせます。元ファイルや接続先、会員が違えば送信を再開しません。正常終了後もstateを残し、確定応答を失った場合の確認に利用できます。確定を繰り返しても別ファイルを追加しません。

通信切断では自動的な再接続・予約取り消しを行いません。利用者が `--resume` または `--cancel` を選択します。予約開始の応答を失いIDが不明な場合は、重複予約を避けるため自動で開始し直しません。管理者が `FILEAUDIT` / `vaultctl audit` で当該主体の予約を確認し、状態確認・取り消しを行ってください。容量不足や権限拒否など、開始されなかったことが明確な応答の場合はstateを再試行可能な状態へ戻します。

既知のIDが記録されたstateは、公開済みなら確定結果を確認でき、未公開なら継続・取り消しが可能です。公開後の `--cancel` は拒否します。公開を取り消す場合は管理者が `FILEHIDE` を使います。元ファイル・公開済み実体を送信クライアントが削除することはありません。

## コネクタの境界

```text
認証済みセッション ── 主体ID・権限の再解決
                           │
行コネクタ（line-v1） ── TransferBackend ── 保管庫アダプター ── Vault
将来のZMODEM等 ────────────┘
通信経路: TCP/Telnet、SSH転送、将来のCOM/Web
```

| 層 | 実装 | 責務 |
| --- | --- | --- |
| 認証入口 | identity_legacy.c / vault_bridge.c | 要求ごとに現会員の停止状態・認証世代・権限を解決 |
| 共通の転送契約 | transfer.h | info / read / start / write / status / finish / cancel とバイト列・メタデータ |
| 行形式コネクタ | transfer_line.c | コマンド解析、Base64、フレーム検証、応答整形 |
| 保管庫への接続 | vault_transfer.c | 型付き要求を既存の保存APIへ接続 |
| 保存・所有者確認 | vault.c | 容量予約、一時保存、ハッシュ照合、公開・取消・履歴 |
| クライアント契約 | TransferConnector | 共通の送受信操作。送信・受信の手順はプロトコルを扱わない |
| 現クライアントコネクタ | LineConnector / Protocol | TCP/Telnet通信とline-v1の符号化・応答検証 |

`TransferBackend` は関数表を持ちます。行コネクタを保管庫実装なしでリンクし、別のメモリ実装へ接続する試験を用意しました。クライアントも別実装のコネクタで送受信手順を実行する試験を用意しています。共通の型・結果コードは現在の保管庫ドメイン型を再利用しますが、コネクタは保存ファイルや会員DBを開きません。

クライアントの `--connector line-v1` は省略可能です。新しいクライアント側コネクタは `TransferConnector` を実装して `CONNECTORS` に登録します。サーバー側も同じ型付きの保存要求へ接続します。現在はソースコード上の差し替え境界で、動的プラグイン読み込みではありません。

## ZMODEMなどを追加するとき

今回の契約は「転送プロトコルのバイト列」と「保存・認可」を分離するものです。既存プロトコルエンジンそのものや、エンジンが使うプロセス／端末制御は別途必要です。

現在の端末経路は行入力・編集を行います。将来のバイナリ転送では、転送開始から終了までメニュー・プロンプト・入力編集を混入させない専用モードを設け、通信制御・切断・中止から通常画面へ戻す処理を実装します。転送中も認可を再確認し、ログイン時の主体を永久に使い回さない設計を維持します。

現在の保存APIは開始時にサイズと期待SHA-256を要求します。既存送信ソフトと接続する際は、渡せるメタデータ・検証情報に合わせて受信手順を設計する必要があります。ZMODEMのフレームを今回の行コマンドにそのまま流すことはできません。実際の既存端末との互換試験を伴う次段階の作業です。

## line-v1の通信仕様

専用クライアントがRAW表示に切り替えて使用します。通常のメニュー画面では転送コマンドを拒否し、HELP FILESを案内します。RAW表示でもTelnetの通信制御は維持されます。

| 要求 | 応答 |
| --- | --- |
| `FILEMETA id` | `FILE id size sha256` と `END FILE` |
| `FILEGET id offset` | `FILEDATA id offset count base64` |
| `FILESTART size sha256 name64 description64` | `UPLOAD id` |
| `FILEPUT id offset base64` | `RECEIVED id next_offset` |
| `FILESTATUS id` | `UPLOADSTATUS id ACTIVE/COMMITTED/CANCELLED received size sha256` |
| `FILEFINISH id` | `UPLOADED id size sha256` |
| `FILECANCEL id` | `UPLOAD CANCELLED id` |

名前・説明はUTF-8をBase64化します。空の説明には `-` を使用します。ハッシュは小文字16進64文字。入力行の上限1024バイトに収めるため、送信チャンクは672バイト、受信チャンクは最大768バイトです。改行・NUL・不正UTF-8やパスとして使える表示名は保存APIでも拒否します。サーバー上の保存先パスを要求に含めません。

チャンク書き込み・状態確認・確定ごとに、現時点の認証を確認します。一般会員は自分の予約だけ操作できます。管理者は他人の予約の確認・取り消しが可能ですが、他人としての書き込み・確定はできません。

## 現時点の制限

容量、同時予約数、途中データ、履歴枠、取り消し方針は [UPLOAD.md](UPLOAD.md) と共通です。転送の自動期限切れ、一般端末の既存転送プロトコル、Web画面、COMドライバーは未実装です。

stage37では保管庫I/Oを専用ワーカーへ移しました。会員管理は掲示板ワーカーに残し、確定直前に接続・認証世代を再確認します。詳しい境界と制限は [BINARY_TRANSFER.md](BINARY_TRANSFER.md) を参照してください。

stage36のクライアントはFILEMETA等を使うため、サーバーもstage36へ更新してください。今回の保存レコード形式はstage35から変更していません。既存BBSサービスの入替・自動起動設定・実データの変更は、この開発作業では行っていません。
