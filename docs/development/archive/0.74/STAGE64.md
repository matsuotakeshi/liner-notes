# Liner notes stage64

今回の範囲は、掲示板・保管庫の階層権限、入会と新着巡回、読書・編集操作、上限拡大、SQLite索引、添付一括取得です。旧RTBBSの画面・キー配置すべての同一再現ではありません。旧データとIDを維持しながら拡張しています。

## 導入とビルド

FreeBSDのC11コンパイラ、OpenSSL、SQLite 3（FTS5とtrigram対応）、Python 3が必要です。SQLiteは `pkg install sqlite3` で用意できます。検証環境と結果は `evidence/stage64/VERIFICATION.md` に記録しました。

```sh
make -j3
make test-stage64
# SQLiteを標準以外の場所へ入れた場合
make SQLITE_CFLAGS='-I/path/include' SQLITE_LIBS='-L/path/lib -lsqlite3'
```

既存サーバーを停止し、先に `scripts/maintenance.py backup` でデータディレクトリ全体を保存してください。作業用コピーで起動・確認してから切り替えます。stage64で上限を超えたデータを作った後は、旧実行ファイルへ戻せません。戻す場合は、旧実行ファイルと導入前のバックアップを組み合わせます。本パッケージは稼働中のサービスや起動設定を自動変更しません。

既存の起動方法に以下を追加できます。指定しなければ従来どおり自由ID・簡易登録です。

```sh
./runtime --telnet --menu --id-mode free --registration-form simple \
  --admins admins.txt --vault-dir vault 2222 notes.dat members.dat
# 自動採番＋詳細フォーム＋承認制の組み合わせ
./runtime --telnet --menu --id-mode auto --registration-form detailed \
  --registration approval --admins admins.txt --vault-dir vault \
  2222 notes.dat members.dat
```

daemonのrc.confでは `liner_notes_id_mode="auto"`、`liner_notes_registration_form="detailed"` を設定できます（既定はfree/simple）。

外部接続は既存の `--bind`、daemon化は既存のrc.d設定、転送は既存の `--zmodem-helper` を引き続き使います。既存helperがソース内の `scripts/zmodem_host.py` を参照していることを確認してください。別ディレクトリの旧スクリプトを参照するhelperは新パッケージに合わせて再生成します。

## SIGOPとグループ

- 掲示板は親ボード、保管庫は親パスのSIGOPを子孫へ継承します。兄弟や別のフォーラムへは広がりません。表示と実際の管理権限は同じ判定を使います。
- 全体管理者が `SIGOPGROUP ボード番号 グループ番号` で委任します。対象グループはそのボードの閲覧／投稿ACLに必要です。グループ番号0で委任解除。
- 委任されたSIGOPは対象ボードを選択し、`GROUP 会員番号 グループ番号` / `UNGROUP 会員番号 グループ番号` を使用します。未委任グループと保護された管理者は変更できません。SIGOPが自分でACLを追加しても、そのグループの管理権限は得られません。
- `BOARDGROUP ボード番号 旧グループ 新グループ CONFIRM` は全体管理者用です。ボードの閲覧・投稿ACL変更と、該当する全会員の所属移し替えをまとめて行います。委任設定も移します。同じグループを使用する他ボードの会員にも影響します。接続中の権限を更新し、他の接続は再ログインが必要です。
- グループ移行はSQLiteへ処理予定を確定してから各保存領域を更新します。途中失敗時は通常操作を止め、次の起動で残りを回復します。

## 読書と新着巡回

```text
FIND SUBTREE * 語句
SCAN DESC SUBTREE 投稿者 語句
SCAN ASC ALL * *
MAIL SCAN DESC
MAIL GET 123
CHECK ARTICLES
CHECK NEXT
CHECK DONE
```

`SUBTREE`は選択したフォーラムと子孫だけです。連続表示で子ボードへ移動しても開始時の検索範囲を維持します。`ASC`は昇順、`DESC`は降順。連続読み出し中はEnter/CONTINUEで次、`+`/`-`で方向切替、`+N`/`-N`でIDを相対移動してから条件に合う記事・メールを探し、STOPで終了します。非公開・削除済みの内容を飛ばすため、Nは「見える記事の件数」ではありません。

`MAIL GET [番号]`（メール内G）は、その人が閲覧できる本文を共通編集バッファに取り込みます。編集時の `/BUFFER` で利用します。送受信者以外には管理者も読めません。

新着は主メニューで `CHECK ARTICLES` / `CHECK MAIL` / `CHECK FILES`。種類別・会員別に前回日時を保存します。最後までCHECK NEXTで表示した後、CHECK DONEで今回開始時の日時を確定します。中断・切断では進めません。初回は過去分も対象です。日時の精度が秒のため境界の同じ秒は重複表示することがありますが、巡回中に到着した内容を次回から落とさない設計です。記事の既読フラグとは独立しています。

## ファイルボードと登録後の操作

```text
FILEBOARDPASS games
FILEUNLOCK games
FILEBOARDPASS games NONE CONFIRM
FILEBOARDOPTIONS games|MENU 10 100
FILEBOARDOPTIONS games/action|BOARD 20 50
FILERENAME 123 NEWNAME.LZH
```

パスワードは非表示入力・salt付きPBKDF2保存。親も保護されていれば親から順に解除します。解除状態は接続中だけで、ログアウト・パスワード変更で失効します。閲覧／登録のレベル・グループ制限は引き続き必要です。管理者・担当SIGOPには管理上のアクセスを認めます。

OPTIONSは「種類・配置番号・取得履歴保持件数」です。MENUにはファイルを登録できず、既存ファイルや進行中の登録があるボードをMENUへ変える操作は拒否します。少ない配置番号が先に表示されます。保管庫の保持件数0は無制限です。古い取得明細は保存領域から整理し、累計取得回数は保持します。BBSの閲覧ログ保持0（記録なし）とは意味が異なります。

登録名変更は全体管理者・親を含むSIGOPに限定します。内部の数値ID・格納ファイル名・内容のハッシュは変わりません。パス区切りを含む名前は拒否します。担当SIGOPは説明、登録者、属性、公開状態、削除も担当範囲で扱えます。別ボードへ分類変更する場合は両側の管理権限が必要です。

## 入会とプロフィール

`--id-mode free|auto`で自由名とシステム採番を選びます。autoは `u000001` 形式（既存名との衝突は回避）。会員番号・削除済みログイン名は再利用しません。旧RTBBSの具体的なID表記を完全再現するものではありません。

`--registration-form detailed`は氏名、カナ、住所、電話、誕生日、機種、ハンドル、地域、職業、趣味、Web、連絡先、紹介元BBS、SYSOP宛メモを順番に入力します。空欄は省略できます。従来のopen/approval/closedと組み合わせられます。個人情報の既定公開範囲は非公開で、紹介元とメモは管理者の申請確認用です。

- `APPLICATION 会員番号`: 承認待ち申請の詳細確認。
- `APPLICATIONSET 会員番号 項目 値`: 申請の修正。FROMBBS/SYSOPNOTEも対象。
- `APPROVE 会員番号`: 承認。
- `MEMBERPROFILE 会員番号 項目 値`: 管理者による会員プロフィール変更。公開設定は維持。

## エディタ

ラインエディタのUは、連続入力を受けて3秒の無入力でコマンド入力へ戻ります。投稿は自動では行いません。Aは従来の手動追記です。検索Sは一致件数と行を表示し、メニュー端末では行内の最初の一致を強調します。0で終了時の確認を表示し、Wで書き込み、Eで編集継続、Qで取り消します。`.`、/SAVE、Undo、プレビューは継続利用できます。

## 新しい上限

| 対象 | 上限 |
|---|---:|
| 累計会員番号 | 999,999（永久欠番） |
| 掲示板・ファイルボード | 各1,024 |
| 1入力行 | 4,096バイト |
| 記事・メール本文・記事／メール下書き・共通バッファ | 256KiB（改行込み） |
| 1ファイル | 1GiB |
| 一括転送 | 16ファイル／16GiB |
| 同時接続 | 128 |
| 同時転送エンジン | 24 |

KB/GBの指定は従来に合わせて1024進のKiB/GiBとして扱います。長文プロフィール・案内文は従来の個別上限を維持します。保管庫・メール添付の総容量既定値は各16GiBへ拡大しました。既存 `limits.conf` に256MiBなどが指定されている場合はその値が優先です。設定例は `vault-limits.example.conf`。ファイルID／イベント数の運用上限は従来どおり設定可能で、0で無制限（保存形式上のID上限内）。同一会員の同時アップロード枠2は維持します。

## DBと保存領域

SQLiteへ会員索引、ログイン名索引、既読ページ、記事・メール・下書きの索引、プロフィールと全文検索を移しました。主要索引の常駐キャッシュは各128件、SQLiteページキャッシュは各2MiBです。3文字以上の検索はFTS5 trigramで候補を絞り、実データと現在の閲覧権限で再確認します。1～2文字やワイルドカード全件は従来の走査です。

既存ジャーナルは耐久保存と復元の原本として残します。`*.article-index.sqlite`などの索引DBは起動時に再構築します。したがって起動時の全データ読み込みや一覧・未読集計の走査まで消えるわけではありません。完全な単一DBへの形式変換ではなく、旧データを保持する段階的なDB化です。SQLiteファイルのディスク容量も確保してください。保管庫・操作履歴等の一部索引は従来方式です。

`notes.dat.features.sqlite`は新着日時・委任・申請メモ・移行予定の**原本**です。再構築できる索引DBと混同して消さないでください。バックアップは保存ディレクトリ全体を対象にします。内部に会員・メール情報を含むため各DBのアクセス権も保護しています。

## 管理ツールによる本文回収

```sh
# 停止して作ったバックアップから、別ディレクトリへ整理済み復元
python3 scripts/maintenance.py compact backup.tar.gz restored64 --reclaim-withdrawn
# 全保存領域の整理もまとめて実施する場合
python3 scripts/maintenance.py compact backup.tar.gz restored64-all \
  --all-stores --tools-dir . --reclaim-withdrawn
```

WITHDRAW済み記事の本文だけを短い空行へ置換し、ID・題名・著者・返信関係・履歴を保持します。HIDEだけの記事は回収しません。検索用DBも復元先で破棄して再構築させるため、そちらに旧本文を残しません。元データと元バックアップは変更しません。バックアップには旧本文が残る点は運用上の保存方針に従ってください。

## 添付一括ダウンロード

`ZMAILDOWNLOADALL メール番号`で最大16添付を1回のZMODEMセッションで取得できます。各添付の権限とハッシュを検証し、送受信者だけが取得できます。公開保管庫を無効にした運用にも対応します。同名ファイルはIDを前置して区別します。転送失敗時にも一部ファイルは相手へ届いている場合があるため、完了応答を確認してください。添付の一括アップロードは今回の対象ではありません。
