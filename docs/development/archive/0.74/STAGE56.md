# stage56: 上限・表示・一括転送・エディタ

## 起動と設定

```sh
./runtime --telnet --menu --bind 0.0.0.0 --lang ja \
  --menu-dir "$PWD/menus" --banner "$PWD/banner.txt" \
  --max-articles 0 --max-mail 0 --max-user-posts 0 \
  --admins "$PWD/admins.conf" --vault-dir "$PWD/vault" \
  --zmodem-helper "$PWD/zmodem-helper" \
  2222 "$PWD/notes.dat" "$PWD/members.dat" "$PWD/boards.conf"
```

既存のデータ・管理者・ボード・保管庫・helperの実際の場所に合わせてください。
稼働中データを試験用データで置き換える必要はありません。rc.dにも
`liner_notes_max_articles`、`liner_notes_max_mail`、`liner_notes_max_user_posts`、
`liner_notes_banner`を追加しました。

| 設定 | 内容 | 既定値 |
|---|---|---|
| `--max-articles N` | 全ボードを合計した累計記事数 | 0 |
| `--max-mail N` | 全会員を合計した累計送信メール数 | 0 |
| `--max-user-posts N` | 会員ごとの全ボード累計投稿数（返信を含む） | 0 |

0は運用上の件数制限なし。削除・取り消し分も累計に含みます。会員ごとの投稿制限は
旧実装にはなく、今回新設しました。会員数1,000の制限とは別です。
制限値を既存データより小さくしても読込みは可能で、新規投稿・送信だけを止めます。
保管庫・添付の制限には影響しません。

記事・メールの配列、非表示・取り消し・改題情報、既読ビットマップ、未読集計を
動的に確保し、番号解析と整理ツールの10,000件前提も除去しました。
IDは削除・整理で詰めず、最大使用番号の次を使います。
既存記事の上位ビットは可変長レコードの印なので、IDの形式上限は
2,147,483,646（次ページカーソル用に1番号を予約）です。メールも同じID範囲。
操作履歴の32ビット連番、使用可能メモリ・ディスク等の物理上限は残ります。
現在は本文もメモリに展開するため、制限なしが無限の容量を保証するわけではありません。

保存形式は変えていません。10,000件を超えたデータは旧版では開けません。
旧版へ戻す場合は更新前バックアップ一式を使用してください。
`notes_compact.py`は引き続き停止中のコピー出力で、記事ID・メールID・返信関係を維持します。

## メニュー・HELP・バナー

- 標準メニューの各機能欄のHELP案内を削除し、案内・終了の `H` に統一。
  `HELP MAIL` 等の直接コマンド、編集中 `/HELP` は維持。
- HELP一覧は RTBBS 5.3βb `SYSTEM/MAINSYS.PAS` の MAINキー順
  A（登録）、B（記事）、C（チャット）、E（編集）、F（保管庫）、I（設定）、
  M（メール）、P（プロフィール）、T（トーク）に対応させ、関連する新機能を隣接配置。
  SYSOPは最後。MAILを短縮キー説明より前へ移動。
  **元の `BBSHELP.JTX` 本文は確保済みソースキットには含まれていないため、
  元ヘルプファイルの行順そのものの一致は未確認**です。
- 一般会員・ゲストには管理メニュー、HELP一覧のADMIN、管理者HELP本文を出しません。
  `HELP ADMIN`を直接指定しても権限エラーです。チャット/保管庫の管理専用説明はADMINへ集約。
- ログイン時に、実際の管理操作が使用する `moderation_admin()` の判定結果をセッションに渡します。
  管理者は外部メニューを独自編集していても管理メニューを表示し、Hから開く一覧にHELP ADMINを必ず表示。
  RAW/MENU切替、再ログイン・ログアウトでも判定を維持・更新します。
- 外部メニューに管理者だけの追加案内を書く場合は、行単独の `[ADMIN]` と `[/ADMIN]` で囲みます。
  旧標準の `[管理者用]` / `[Administrators]` 欄は共通表示から除き、標準管理欄へ置換します。
- `--banner FILE`（既定 `banner.txt`）はUTF-8、最大4KiB。BOM・LF/CRLF対応。
  メニュー接続時に1回表示。存在しない・空・BOMだけなら表示せず通常起動。
  生プロトコル接続には送りません。書換えは次回起動で反映。危険な制御文字、不正UTF-8、
  サイズ超過や読取りエラーは起動時に報告します。

## 一括アップロードと途中再開

途中再開用エンジンを新規ディレクトリにビルドし、**新しいhelper**を生成してください。
旧helperは保存します。既存helperの参照先だけではCRC修正が適用されません。

```sh
python3 scripts/build-lrzsz.py deps/resume
python3 scripts/configure-zmodem.py \
  --receiver "$PWD/deps/resume/local/bin/lrz" \
  --sender "$PWD/deps/resume/local/bin/lsz" \
  --spool-root "$PWD/zmodem-spool56" --output "$PWD/zmodem-helper56"
```

起動オプションは `--zmodem-helper "$PWD/zmodem-helper56"` にします。
ビルド時に保存される `lrz.liner-notes-resume.json` は受信プログラムと一緒に保持してください。
再開時は修正版のハッシュを確認し、未修正エンジンへの無自覚な切替を拒否します。
ダウンロード再開も端末側受信プログラムの実装に依存します（旧lrzsz 0.13.1を使うなら同修正が必要）。

```text
ZUPLOADBATCH open/tools|説明
ZUPLOADBATCH -|ルートへ登録
ZUPLOADIN open/tools|説明
ZRESUME open/tools|説明
ZMAILUPLOAD 説明
ZMAILRESUME 説明
```

一括送信は端末側で複数ファイルを選択します。最大16ファイル、合計64MiB、1ファイル16MiB。
同一登録先・共通説明で登録し、後から各ファイルの説明を管理できます。
ディレクトリ・リンク・同名重複・不正名・超過サイズを拒否し、全ファイルの受信成功を
確認してから公開します。親ボードを含む閲覧権限・登録権限を転送中と登録時に再確認します。

登録はファイルごとに確定するため、登録段階で上限や切断が発生すると、一部だけ公開済みの場合があります。
その場合は `ZUPLOADBATCHRESUME 同じボード|同じ説明` で再試行できます（受信済みの場合は公開処理だけを行います）。
元ファイルと予約ID・SHA-256・公開済み状態を保持し、既に登録したファイルを二重登録しません。
結果不明の予約開始は従来どおり自動で作り直さず、管理者によるFILEAUDIT確認が必要です。
一括転送の通信自体が中断した場合も、`ZUPLOADBATCHRESUME 同じボード|同じ説明` を使えます。
端末で元と同じファイル一式を選択してください。受信済み部分をCRC照合し、完了済みファイルも含めて
全ファイルの完了を確認してから登録します。部分的なファイル集合だけを公開しません。

単一アップロードのTCP切断・転送中断では、非公開の受信途中ファイルをhelperのspoolに保存します。
同じ接続先ポート・会員・公開/メール区分・ボード・説明で `ZRESUME` / `ZMAILRESUME` を実行し、
端末から同じ元ファイルを選択してください。再開時もログインと権限確認が必要です。
元の `ZUPLOAD` を再度実行しても、残った途中ファイルを黙って上書きしません。
管理者が保管先を整理する場合は、転送が終了していることを確認して退避してください。

lrzsz 0.13.1 の `--resume --resume` を使用して保存済み部分のCRCを照合し、
一致時は1KiB境界から続行します。
再開時に限り、既存ファイルを全面禁止するlrzszの制限レベル2から通常の制限レベル1へ切り替えます。
絶対パス・親ディレクトリ参照の拒否と全階層のsymlink拒否は維持し、非公開の受信専用ディレクトリで実行します。境界に満たない末尾部分は再送されます。
内容が異なる場合はlrzsz側で先頭から再転送するため、任意ファイルへの継ぎ足しは行いません。
公開前に全ファイルのSHA-256を計算し、保存した公開再開情報との一致も確認します。
ダウンロードは端末の「途中再開」を選び、同じ保存先を指定します。
端末による途中再開の対応状況は異なります。FreeBSD検証はlrzsz同士で行います。

BBS本体はZMODEMを直接実装せず、既存の認証済みコネクタと別プロセスのエンジンで処理します。
メール用ファイルは今回も非公開領域のままで、SYSOP閲覧の例外を追加していません。

## エディタ

`EDITOR BETA` / `EDITOR LINE` でセッションの入力方式を選択。
編集中は `/EDITOR BETA` / `/EDITOR LINE`。本文はそのまま保持します。
既定は従来と同じベタ入力で、`.`終了と既存の編集コマンドも使えます。

| 方式 | RTBBSに合わせた操作 |
|---|---|
| ベタ | `//` 確定、`/E` ライン編集へ、`/N` 書き直し、`/M` 行番号、`/?` 案内 |
| ライン | 数字で行選択、`E[n]` 1行修正、`A`/`U` 末尾追記、`I[n]` 挿入、`N` 書き直し |
| ライン | `L` 表示、`D` 削除、`Q` 引用符付加、`S` 文字列検索、`M` 行番号、`?` 案内、`0` 確定 |
| 範囲 | `L3-5`、`D-2`、`Q4-` 等。Eは指定開始行を1行修正、Iは指定開始行から挿入 |

追記・挿入中は `//` でラインコマンドへ戻ります。
`/UNDO`、`/PREVIEW`、`/TITLE`、`/REPLACE`、`/INSERT`、`/DELETE`、`/LINES`、
`/SAVE`、`/CANCEL`、メール添付操作は維持。記事・返信・メール・保存下書きに共通です。
`/N`、N、範囲削除、引用付加もUndoの対象です。

RTBBSの `SYSTEM/EDITSYS.PAS` を参照した操作互換で、完全エミュレーションではありません。
Uはペースト追記です。旧DOSのローカルファイル入力、編集内T/W/接続メモ/状態表示、
端末制御コードまでは移植していません。エディタ種別は今回セッション単位で、会員設定への永続保存は未実装です。

## 固定上限の棚卸し（今回は変更しない項目）

| 項目 | 現在 | 設定値化時に必要な主な作業 |
|---|---:|---|
| 会員数 | 1,000 | 会員・権限・通知・プロフィール配列と会員ID検証の可変化 |
| 掲示板数 | 64 | カタログ・ACL・既読集計の可変化 |
| 記事/メール/下書き本文 | 16KiB | レコード読込み・通信・表示バッファの協調変更 |
| 1入力行 | 1,024バイト | 端末・セッション・コネクタの入力契約変更 |
| 保管庫/メール添付の累計ファイルID | 各1,000 | vault配列、転送番号、添付参照表、クライアントの可変化 |
| 保管庫/添付の総容量 | 各256MiB | 64ビット容量カウンタと設定、予約を含む容量計算 |
| 1ファイル | 16MiB | vaultとPythonエンジン、OSファイル上限を同時変更 |
| vaultイベント | 10,000 | 履歴配列・予約確定用枠・整理仕様の変更 |
| 同時アップロード予約 | 全体8 / 会員2 | 予約配列・資源管理の可変化 |
| ファイルボード | 128 / パス48バイト | ボード表・保存形式・UI/コネクタの整合 |
| 一括転送 | 16ファイル / 64MiB | リスト・引数・検証・資源制限の協調変更 |
| 同時接続 / 同時ZMODEM | 32 / 4 | 接続表・チャット参加表・子プロセス上限の協調変更 |
| チャット履歴 / ミュート | 20件 / 会員32人 | 履歴/会員設定形式と表示の可変化 |

数値定義だけを変えて無制限にすると配列範囲・メモリ・ディスク使用量に影響します。
特にvaultの1,000件は削除してもIDを再利用しない累計枠で、容量回収とは別です。
