# AREA-PC88へのDoor認証連携引き継ぎ（開発候補）

確認日: 2026-11-19。Liner Notes PR #135の開発API。正式リリースのAPIではありません。
AREA-PC88は別の開発作業へ引き継ぐ方針であり、このPRでは変更しません。
本番のBBS・ゲーム・設定・保存データを使った試験は行いません。

## 確認した現行コードと差分

対象は `matsuotakeshi/areapc88` のmainコミット
`e0cd980a2f5cc135d3f9b6dc805ea41233b2eb5c` です。実装前に最新との差分も確認してください。

- `c11/src/area_auth.c/.h`: 共有秘密鍵による検証用トークン。
- `c11/src/area_server.c`: `auth_open()`でトークン検証、`auth_session_lookup()`で
  ゲーム独自セッションの期限確認、`auth_allows()`で会員・部屋単位の権限確認。
  `SESSION`の各処理でこれらを呼びます。
- `c11/src/area_lobby.c`: `--token-file`と`--door-env`。
- `scripts/door_lobby_auth_TEST_ONLY.sh`: 事前に発行した会員別トークンファイル。
- `docs/door_auth_prototype.md`: 検証用仕様・制約。

今回のBrokerはこのHMAC形式を発行しません。単純にトークンを書式変換したり、
既存の発行秘密鍵をDoorへ渡したりして接続しないでください。チケット消費後も、
BBS切断・Broker停止をゲーム側が検出できる照会経路が必要です。

## 役割と配備境界

| プロセス | OSユーザー | 許可する役割 |
| --- | --- | --- |
| BBS | 既存BBS専用 | Coreで会員認証、隔離起動要求 |
| 隔離起動サービス | root | 固定された実行先・UIDで起動、チケット発行要求 |
| Broker | Broker専用 | 消費・失効・有効性の管理 |
| `areapc88lobby` | 同時実行枠ごとの専用UID | 受領チケットをゲームサーバーへ一度だけ送る |
| `areapc88d` | ゲームサーバー専用 | Brokerのconsume/check、既存のゲーム権限判定 |

すべて別UIDです。Broker有効時は旧Doorも例外なくBBSと別UIDです。
ゲームサーバーのUIDはBrokerの`consumers`でDoor IDと結び付けます。
スロットUIDは発行者にも消費者にも登録しません。保存DB・秘密情報は
ゲームサーバーだけが読み書きできる場所へ置きます。

Brokerの消費APIはローカルUnix socket限定です。別ホストのゲームサーバー向けの
安全な通信路は未実装です。今回の連携試験は同じ隔離ホスト内で行ってください。

## ロビー側の変更依頼

1. `LINER_AUTH_FD`に指定された継承FDから、改行まで最大65バイトを読み、
   64文字の小文字16進チケットを受け取ったらFDを閉じる。
2. チケットを既存ゲームサーバーへの保護された接続で送る。
   `--token-file`の事前発行、argv、環境変数の値に秘密を載せる方式へ戻さない。
3. `LINER_USER_ID`・`LINER_USER`は表示・整合確認用にとどめ、サーバーが返した
   認証主体を使用する。表示名の変更で別パイロットを取得させない。
4. 再接続には新しいBBS/Door起動で新チケットを取得する。
   期限切れやBroker停止を、検証用無認証モードで回避しない。

これらは追加する機能の指定です。現行の`areapc88lobby`がFD読取に対応している
という意味ではありません。オプトイン用のCLI名はAREA-PC88側で確定してください。

## ゲームサーバー側のAPI

参照実装は `scripts/door_auth_client.py`。C側へ実装する場合も同じ制約を守ります。
受け付ける接続先は管理者が固定したUnix socketです。接続時にOSのpeer credentialsで
相手が設定したBroker UIDであることを確認し、確認できなければ秘密を送らず拒否します。
FreeBSDは`getpeereid`、Linuxは`SO_PEERCRED`、Solarisは`getpeerucred`を使用します。

1要求につき1接続、UTF-8 JSON＋LF、最大4096バイト、既定3秒で期限切れです。
例の`<ticket>`・`<lease>`は実際には64文字の16進文字列です。

```json
{"op":"consume","door":1,"bbs":"my-bbs","token":"<ticket>"}
```

成功結果は`{"ok":true,"result":{"lease":"...","claims":{...}}}`。
claimsは以下の組で、ゲーム独自セッションへ保存してください。

| フィールド | 用途 |
| --- | --- |
| bbs | BBS識別子 |
| member | Coreが認証した会員番号（整数） |
| door | 対象Door ID（整数） |
| session | 発行された接続識別子（文字列） |
| generation | 認証世代（0も正当な値） |
| ticket_id | チケット識別子 |
| expires_in | 残り秒数。キャッシュを許可する期間ではない |

ゲームサーバーだけがleaseを保持します。ロビーへleaseや署名鍵を返す必要はありません。
ロビーへ返すゲーム独自セッションは既存のランダムcapabilityを利用できます。

```json
{"op":"check","door":1,"bbs":"my-bbs","token":"<lease>"}
```

成功は`{"ok":true,"result":{...claims...}}`。
失敗は`{"ok":false,"error":"authorization denied"}`。通信障害、不明な形式、
UID不一致、タイムアウトも認証失敗として扱います。チケットの再利用は拒否されます。

`SESSION`の各要求に対し、`auth_session_lookup()`の後、ゲーム処理の前にcheckを行い、
上記の識別子組が初回consume時と一致することを確認します。その後、既存の
`auth_allows()`を通します。会員の資産だけでなく、個別履歴・部屋イベントなどの
保護対象の読み取りにも適用してください。接続時だけの一度きりの照会は不十分です。

BBS切断・時間制限・Broker停止後の要求を拒否し、既存ゲームのデータ処理を開始しません。
新しい接続へ置き換えた後、古い接続の終了処理が新しい席・認証を失効させないよう、
ゲーム側でも接続世代と既存のpresence leaseを照合してください。

## データ互換と認証切替

既存の戦闘式・報酬・装備・保存形式は変更対象ではありません。
パイロットの永続キーはBBS識別子と会員番号の対応を明示し、複数BBSで同じ番号を
同じ会員とみなさないでください。既存の`LN番号`に結び付ける場合は、単一BBSへの
固定対応を設定で明示し、別BBSからの衝突を拒否します。既存パイロットの再採番や
自動統合は行いません。必要な新しい対応表はゲーム側の通常の移行レビュー対象です。

Brokerモードでは従来の未認証IPCや検証用HMAC認証へフォールバックしません。
従来モードとの明示的な排他設定を設け、どの認証経路が動いているか確認可能にします。
ゲームサーバー再起動で認証セッションは失効してよいものの、コミット済み資産は保持し、
新しいチケットで再入場した本人に復元します。Broker再起動で旧チケット・leaseは無効です。

## 引き継ぎ先で必要な結合試験

- 2名以上の会員、本人パイロットの復元、他会員の操作と非公開データ取得の拒否。
- チケット再使用・偽造・Door/BBS変更・期限切れの拒否。
- BBS切断、Door時間切れ、強制終了、Broker停止後の操作拒否。
- 古い接続の終了と新接続の競合、ゲームサーバー再起動後の保存データ確認。
- RTBBSゲームメニューへの復帰、NAWS、従来の認証なしDoorへの非干渉。
- 不正な接続元UID、FD・環境・ログ経由の秘密漏洩を確認。

Liner Notesの `tests/test_door_broker_linux.py` はこれらの一部を模擬ゲームで検査します。
実AREA-PC88の成功証跡には代用しません。AREA-PC88側の変更ができたら、両リポジトリの
SHAを固定した隔離結合試験を実施し、OS別・正常系／拒否系の結果を報告してください。
