## Findings and fixes

1. `door_processes.py` could open pidfds but could not read another domain's
   `/proc/PID/status`. Add domain-labelled directory search and ordinary file
   getattr/open/read to the isolation supervisor; do not grant ptrace, links,
   file writes or signals to unrelated service domains.
2. The isolation child had capability mask `0x6b`, despite a bounding set `0xeb`;
   `setgroups` and `setgid` succeeded but `setuid` failed. The installed systemd
   was `257-23.el10_2.2.rocky.0.1`. Its behavior matches the
   [upstream v257 exec implementation](https://github.com/systemd/systemd/blob/v257/src/core/exec-invoke.c):
   the seccomp/user path drops CAP_SETUID when it is not ambient. Remove the
   redundant `User=root` from this system-service sample and retain default root,
   `Group=root`, the launcher's UID check and existing bounded capabilities.
   Do not add ambient capabilities or disable seccomp/NoNewPrivileges.
3. During parent SIGKILL recovery, `pidfd_open` returned EINVAL for a process
   whose status had already disappeared (subsequent ENOENT). Confirm that
   disappearance before treating it as the existing process-exit race. A present
   or inaccessible status still fails closed; BUSY is not blindly reset.
4. A successful 25-byte stderr write did not prove journal delivery: a dedicated
   probe found fd 2 pointing to `/null` (character device major 1/minor 3).
   Permit inherited init-owned fd use and stream getattr/read/write, without
   connectto or daemon membership. Both unit and PID journal marker queries then
   succeeded. A trial granting syslogd read access to service sockets did not
   solve the issue and was **not** incorporated.
5. Per-line Python tracing changed supervision timing; after locating failures,
   normal acceptance runs without it. `--trace-permissions` remains an explicit
   CI diagnostic option, with filtering and privacy tests.
